## Phase Goal

**As a** FRC CAD lead, **I want to** click "check now" and get back a structured, rule-cited report for whatever document tab is live at that moment — with an obvious "reconnect" prompt if my session expired, **so that** I can see the full integration chain works end-to-end before trusting any individual verdict.

<objective>
Wire the authorized session (Plan 01) to the pure check core (Plan 02) through a live Onshape data path: a typed openapi-fetch client that injects the session token, a 401-reactive refresh-and-retry wrapper, a POST /api/check route that re-derives live context at click time, and a panel that renders the structured report — plus the dedicated Reconnect state when refresh fails.

This is the slice that turns "authorized + tested logic" into "user clicks check now and sees a rule-cited report." It closes CONN-02 (live context), CONN-03 (transparent refresh vs. distinct Reconnect state), and RUN-01 (structured report).

Purpose: Complete the Walking Skeleton end-to-end so a real click produces a real report from real Onshape geometry.
Output: Typed Onshape client, refresh wrapper, /api/check route, and the report/banner/Reconnect panel components — with supertest + vitest coverage of the route and refresh behavior.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| panel → POST /api/check | Panel supplies documentId/workspaceId; server must not trust the panel for the element to check (re-derives it) nor accept a token from the client |
| backend → Onshape REST API | Server-side calls carrying the session's Bearer token; subject to 401/refresh |
| ReconnectRequiredError → panel | Refresh-failure signal must reach the panel as a distinct state, not leak token/error internals |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-10 | Information Disclosure | OAuth access token | mitigate | Token attached to Onshape requests only server-side in client.ts; /api/check response contains only verdicts + context, never the token; src/panel references no token (grep-enforced) |
| T-01-11 | Spoofing/Tampering | panel-supplied element/document identity | mitigate | The ELEMENT to check is re-derived server-side via getElementsInDocument at request time (CONN-02), not trusted from the client; Onshape's own ACLs (403/404) gate access to the document the token can read |
| T-01-12 | Input Validation | documentId/workspaceId from request body | mitigate | Validate the shape of did/wid server-side before using them in Onshape API path interpolation (RESEARCH Security Domain V5) |
| T-01-13 | Elevation of Privilege | expired/revoked token reuse | mitigate | 401-reactive single refresh-and-retry; refresh failure forces a distinct Reconnect (D-04/D-05), never a silent unauthorized retry loop |
| T-01-14 | Repudiation/Trust | overclaiming an untrusted verdict | accept (by design) | PlumbingBanner explicitly labels verdicts "not yet trusted" for Phase 1 — check correctness is deliberately out of scope until Phases 2-4 |
</threat_model>
