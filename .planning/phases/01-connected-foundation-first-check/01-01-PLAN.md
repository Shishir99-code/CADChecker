## Phase Goal

**As a** FRC CAD lead, **I want to** connect CADChecker to my Onshape document via OAuth and see its panel render inside the document view, **so that** I have a trusted, authorized surface where legality checks will run.

<objective>
Establish the CADChecker Walking Skeleton's first vertical slice: a scaffolded TypeScript/Node/Express + React/Vite project where a user clicks "Connect Onshape" in the embedded panel, completes the Onshape OAuth2 authorization-code flow, and lands back with a server-side session — while the panel renders inside a real Onshape Element-tab iframe and completes the postMessage handshake.

This is the auth + embedding slice of the skeleton. It proves the highest-uncertainty integration surface (Onshape OAuth + cross-origin iframe session) works before any check logic exists.

Purpose: De-risk OAuth and iframe embedding first; every later slice assumes a working authorized session and a rendered panel.
Output: Project scaffold, OAuth routes, passport-onshape config, session cookie handling, panel shell with postMessage handshake, and supertest coverage of the auth entry points.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser iframe (Onshape) → CADChecker backend | Cross-origin fetch/navigation from panel JS; untrusted until session-authenticated |
| Onshape web client → panel (postMessage) | Cross-origin postMessage events; only the captured Onshape server origin is trusted |
| CADChecker backend → Onshape OAuth/token endpoints | Server-side; carries client_secret and tokens |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-01 | Spoofing/Tampering | OAuth authorize/callback flow | mitigate | passport-onshape Strategy configured with state: true — CSRF state parameter validated on callback; never disabled (RESEARCH Known Threat Patterns) |
| T-01-02 | Information Disclosure | OAuth client_secret | mitigate | client_secret read only from process.env in src/server; never referenced under src/panel or bundled by Vite (verified by grep in Task 2 acceptance) |
| T-01-03 | Information Disclosure | access/refresh tokens | mitigate | Tokens stored only in server-side express-session (D-03); callback response sets only the session cookie, never token values in any body |
| T-01-04 | Spoofing/Tampering | panel postMessage listener | mitigate | Listener rejects any event whose event.origin != the server origin captured at iframe load; postMessage payload is never treated as authorization (RESEARCH Anti-Patterns) |
| T-01-05 | Elevation of Privilege | session cookie theft via XSS | mitigate | Cookie is httpOnly + Secure + SameSite=None; React JSX default escaping, no dangerouslySetInnerHTML in the panel |
| T-01-06 | Tampering | npm dependency installs | mitigate | All 14 packages [OK] in RESEARCH Package Legitimacy Audit; vitest [SUS] is a documented false positive (real vitest-dev/vitest) — no unresolved [ASSUMED]/[SLOP] packages, so no install checkpoint required |
| T-01-SC | Spoofing (reliability-adjacent) | Safari third-party-cookie blocking of the session cookie | accept (with disclosure) | SameSite=None; Secure set as the minimum; Safari ITP may still block — Task 4 tests Safari explicitly and records it as a known v1 limitation rather than silently changing token storage (RESEARCH Pitfall 2 / A4) |
</threat_model>
