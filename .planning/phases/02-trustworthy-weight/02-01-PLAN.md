<objective>
Add the two typed Onshape client methods this phase depends on — `getPartStudioMassProperties` and `getPartsMetadata` — following the existing `getAssemblyDefinition` `callWithRefresh` idiom, then verify their live JSON responses against a real Onshape document so the downstream merge-step contract is locked before any weight math is written.

This plan exists because the entire phase rests on two live-unverified assumptions (RESEARCH A1/A2, Open Questions 1-2): whether `BTMassPropertiesInfo.mass[0]` is the correct nominal-kg index, and whether raw REST mass is always SI kg regardless of document display units. It also confirms the join-key chain (`BTAssemblyDefinitionInfo.parts[]` carries `partId`) and the material-absence detection rule (`BTPartMetadataInfo.material` present vs absent) that 02-02's enrichment merge and 02-03's weight verdicts assume. Getting these wrong would silently compute wrong weight numbers — the worst possible failure for a trust-first tool.

Purpose: De-risk the new Onshape mass/material API surface (Phase 1 only exercised elements + assembly-definition) and produce a written, human-confirmed contract note that 02-02/02-03 treat as ground truth.
Output: Two new typed methods on `OnshapeClient` (+ unit tests), and `02-MASS-PROPERTIES-CONTRACT.md` recording the live-confirmed findings.
</objective>

| T-02-02 | Tampering | new method path params (`did`/`eid`/`partIds`) | mitigate | Methods take only typed string args; in 02-02 these MUST be derived server-side from `definition.parts[]` (already server-fetched), never from `req.body` (continues T-01-11/CONN-02). | T-02-04 | Spoofing/Elevation | expired/invalid access token on new calls | mitigate | Both methods route through `callWithRefresh`, inheriting the exact 401→refresh→retry→ReconnectRequiredError behavior (D-04/D-05) already proven in Phase 1 — no bespoke auth handling. |
