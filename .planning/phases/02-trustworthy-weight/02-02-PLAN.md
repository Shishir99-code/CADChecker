<objective>
Extend the shared facts + verdict shapes and ship the material-default audit end-to-end so a user can click "Check Now" and see the exact set of weight-contributing parts Onshape would otherwise silently omit from the mass total.

This is the phase's breaking-change slice: `Fact` gains `massKg`/`materialAssigned`; `flatten-assembly.ts` surfaces the assembly `parts[]` join list and a `groupPartsByElement` helper; `Verdict` becomes tri-state (PASS/FAIL/UNKNOWN) with an optional dual `measured:{lb,kg}`, `affectedParts`, `caveats`, and a single documented `KG_TO_LB` constant (D-02, D-06, D-11). Every Phase-1 consumer of the old `Verdict` (`occurrence-count.check.ts`, `frame-tag-presence.check.ts`, the panel's mirrored `CheckReportVerdict`, and `ReportTable.tsx`) is migrated in lock-step so the build stays green. The route (`check.routes.ts`) performs the per-Part-Studio mass + material fetch/merge between fact-gather and engine-run — checks stay pure and synchronous. A new `material-audit.check.ts` (WGHT-01) lists offending parts and is registered as a first-class report row.

Purpose: Success Criterion 1 — the material audit is visible and trustworthy. It is the gate the two weight verdicts (shipped in 02-03) will depend on.
Output: Extended `Fact`/`Verdict` contracts, two new typed Onshape client methods, the enrichment merge step, and the shipped material-audit check rendered in the panel.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| panel (browser iframe) → backend `/api/check` | Untrusted `documentId`/`workspaceId` cross here; the element and all part/Part-Studio ids are re-derived server-side, never trusted from the client. |
| backend → Onshape REST API | Session-scoped OAuth token attached server-side only; new mass/material calls must route through the same authenticated client. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-01 | Tampering | mass/material fetch scoping in check.routes.ts | mitigate | Derive `did`/`eid`/`partIds` exclusively from the server-fetched `definition.parts[]` (Task 2), never from `req.body` — continues T-01-11 / CONN-02. Blocks a client from pointing the mass query at another element. |
| T-02-02 | Information Disclosure | enriched Fact/Verdict data (part names, paths, masses) returned to the panel | mitigate | Response carries only the authenticated session's own document data, re-derived server-side from the session-scoped OAuth token; no cross-tenant id is ever accepted from the client. Panel re-derives no business logic (D-02: conversion done once server-side). |
| T-02-03 | Denial of Service | per-part Onshape API fan-out | mitigate | Use bulk `getPartStudioMassProperties`/`getPartsMetadata` grouped per distinct Part Studio element (O(distinct elements), not O(parts)) — RESEARCH Anti-Patterns; avoids rate-limit exhaustion of the user's own Onshape account. |
| T-02-SC | Tampering | npm/pip/cargo installs | accept | This plan introduces ZERO new packages (RESEARCH Package Legitimacy Audit: 100% additive use of already-audited `openapi-fetch`, generated `onshape.d.ts`, `vitest`). No install task exists; no legitimacy checkpoint required. |

No high-severity unmitigated threat remains, so no blocking human checkpoint is required for this plan.
</threat_model>
