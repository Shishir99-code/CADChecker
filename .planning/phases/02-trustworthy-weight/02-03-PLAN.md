<objective>
Ship the two trustworthy, distinctly-filtered weight verdicts over the enriched `Fact[]` that Plan 02-02 lands: `robotWeightCheck` (R103 = total mass − `BUMPER_` parts − `BATTERY_` parts) and `robotBumpersWeightCheck` (R408 = total mass − `BATTERY_` parts, bumpers included). Each is an independently-filtered occurrence computation (not one number relabeled, per D-05 / WGHT-04). Each produces `UNKNOWN` — suppressing the number entirely — when any part in its OWN included set lacks material or a resolved mass (per-verdict gating, D-09/D-10 / WGHT-02). Each emits a missing-tag caveat when its `BATTERY_`/`BUMPER_` tag is absent (D-06). Both render `<lb> lb (<kg> kg)` off the canonical-kg total via the single `KG_TO_LB` constant (D-01/D-02). Also correct `rules/2026.json` R103/R408 `unit` from `kg` to `lb` (D-03) and register both checks in `buildEngine()`.

Purpose: Deliver Success Criteria 2, 3, and 4 — a robot-only and a robot+bumpers weight verdict the team can trust, gated so a wrong number is never shown on incomplete mass data.
Output: Two new pure `CheckFn` files with vitest coverage, a two-field config fix, and their registration in the check route.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| enriched `Fact[]` → check functions | Facts are derived server-side (02-01/02-02) from the already-validated documentId/workspaceId and Onshape's own assembly definition; the checks in this plan consume that internal, already-trusted data. No new external input crosses into this plan. |
| verdict → panel render | Verdict fields (part names, paths, caveats) flow to the panel; all originate from the team's own authorized document. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-03-01 | Integrity/Tampering | included-mass reduce in robot-weight/robot-bumpers-weight checks | mitigate | Gate to UNKNOWN when any included part has `massKg === undefined` (enrichment gap), not just `materialAssigned === false` — prevents a materialed part whose mass failed to resolve from silently contributing 0 kg and flipping a FAIL to PASS. Enforced by Task 1 Test 5. |
| T-02-03-02 | Spoofing (naming) | `BATTERY_`/`BUMPER_` prefix filters | accept | A team could name a heavy part `BATTERY_x` to exclude it from R103. No privilege boundary is crossed — the team is checking its own robot; the read-only prefix convention (D-04) is the team's own design authority. Documented, not mitigated. |
| T-02-03-03 | Information disclosure | affectedParts {name, path} in Verdict | accept | Part names/paths come from the user's own authorized document; disclosure is to the same user. No PII, no cross-tenant exposure. |
| T-02-03-04 | Denial of service | reduce/filter over `Fact[]` | accept | Facts array is bounded by the assembly already fetched upstream; O(n) filter/reduce over that bounded set adds no new unbounded work. Low value target. |
| T-02-03-SC | Tampering (supply chain) | npm/pip/cargo installs | accept (N/A) | This plan installs NO packages — all dependencies (vitest, the engine/config modules) already exist from Phase 1 and 02-01/02-02. No install task, no `[ASSUMED]`/`[SUS]` package to gate. |
